# toco.id — досье разведки (этап 0)

**Дата:** 2026-08-30
**Статус:** ⚠️ **НЕЗАВЕРШЕНО.** Прямой доступ к `toco.id` из среды, где выполнялась
разведка, заблокирован egress-политикой (см. «Ограничение среды»). Всё, что ниже,
разделено на два блока: **подтверждённое** (получено из поискового индекса) и
**гипотезы** (требуют проверки живыми запросами).

Ничего в этом файле не следует считать готовым контрактом API, пока не пройдены
шаги из раздела «Как добить этап 0».

---

## Ограничение среды

Сессия работает через policy-enforcing egress-прокси, который по умолчанию
запрещает всё. Проверено:

| Хост | Канал | Результат |
|---|---|---|
| `toco.id:443` | curl (CONNECT) | `403` — `connect_rejected`, «policy denial» |
| `toco.id` | WebFetch | `EGRESS_BLOCKED` |
| `partners.toco.id` | WebFetch | `EGRESS_BLOCKED` |
| `www.toco.id`, `api.toco.id` | curl | таймаут/отказ туннеля |
| `play.google.com`, `medium.com`, `en.wikipedia.org`, `example.com` | curl / WebFetch | заблокированы |

То есть закрыт не только `toco.id` — политика default-deny для всего исходящего
трафика. Единственный рабочий канал — поисковый индекс (он ходит не через
egress-прокси). Поэтому в досье попало только то, что видно из поисковой выдачи:
URL-структура и подписи страниц. Ни один HTTP-ответ `toco.id` в этой сессии не
был получен, DOM не открывался, вкладка Network не снималась.

Разблокировка — в настройках network policy окружения:
<https://code.claude.com/docs/en/claude-code-on-the-web>

## 1. Что подтверждено

### 1.1. Профиль площадки

Toco — индонезийский маркетплейс без комиссии (запуск 2024), совмещающий
классическую модель marketplace с досками объявлений (*iklan baris*). Категории:
fashion, beauty, электроника и гаджеты, автомобили/автозапчасти, дом, услуги.
Есть веб-версия, Android (`id.toco`) и iOS (`id1537732731`).

Поддомены:

| Поддомен | Назначение |
|---|---|
| `toco.id` | публичная витрина (цель парсера) |
| `seller.toco.id` | кабинет продавца — **вне области работы**, требует авторизации |
| `try.toco.id/seller` | лендинг онбординга продавцов |
| `partners.toco.id` | «Omni Open API» — партнёрская документация, аутентификация через HMAC-подпись |

> `partners.toco.id` — **не** тот API, что нужен боту: это партнёрская интеграция
> с ключами, выдаваемыми по договору. Публичный парсинг витрины должен
> опираться на тот же внутренний API, который дёргает сама веб-версия.

### 1.2. URL-структура (подтверждена реальными URL из индекса)

```
/                                     главная
/listing/<slug>                       карточка товара/объявления
/store/<store-slug>                   витрина продавца
/p/<кат>/<подкат>/<под-подкат>        категорийный браузинг
/classified                           раздел объявлений (iklan baris)
/classified/search                    поиск по объявлениям
/id/search?q=product%2Fsearch&search= поиск по товарам (locale-префикс /id/)
/article/<slug>, /faq, /about, /terms, /register   статика
```

Живые примеры, на которых это подтверждено:

- `/listing/relaxon-1783954752557-b437`
- `/listing/vape-bekas-1768994453223-3c74`
- `/listing/jual-kompor-portable-bekas-1755842735314`
- `/listing/jual-speaker-bekas-1755844134333`
- `/listing/gundam-bekas-borongan`
- `/listing/laptop-gaming-asus-rog-strix-rgb-intel-core-i7-gtx-bekas-murah`
- `/store/review-in`, `/store/14-garage`, `/store/barokah-doa-ibu`, `/store/axl-studio`,
  `/store/tokoh-elektronik`, `/store/om-mobilindo`, `/store/findit-id`
- `/p/otomotif/interior-mobil/cover-dashboard-mobil`

### 1.3. 🔑 Ключевая находка: epoch-ms в slug объявления

Часть slug'ов оканчивается 13-значным числом — это Unix-время в миллисекундах,
и оно правдоподобно ложится на дату публикации:

| Slug | epoch ms | Дата (UTC) |
|---|---|---|
| `relaxon-**1783954752557**-b437` | 1783954752557 | ≈ 2026-07-13 |
| `vape-bekas-**1768994453223**-3c74` | 1768994453223 | ≈ 2026-01-21 |
| `jual-kompor-portable-bekas-**1755842735314**` | 1755842735314 | ≈ 2025-08-22 |
| `jual-speaker-bekas-**1755844134333**` | 1755844134333 | ≈ 2025-08-22 |

Все четыре значения попадают в прошлое относительно текущей даты (2026-08-30) и
распределены по времени — на случайный хеш не похоже.

Наблюдаются три формы slug:
`<текст>-<epoch_ms>-<hex4>`, `<текст>-<epoch_ms>`, и просто `<текст>`.

**Что это даёт фильтру `only_recent`:** если гипотеза верна, для части объявлений
дату публикации можно получить **бесплатно, прямо из URL в листинге**, без
дозапроса карточки. Это радикально дешевле, чем N+1 запрос на каждый товар.

**Что нужно проверить:** (а) действительно ли это `created_at`, а не время
последнего редактирования/переиндексации; (б) какая доля объявлений имеет суффикс
(slug'и без него — старые? или созданные другим путём?); (в) совпадает ли значение
с датой, отрисованной на карточке. Проверка — сверить 20–30 карточек: epoch из URL
против даты на странице. **До этой сверки использовать значение как дату публикации
нельзя** — только как кандидат с последующей верификацией.

### 1.4. Серверная сортировка и фильтры

На страницах поиска и витрин продавца присутствуют элементы «Filter» и «Urutkan»
(сортировка) со значениями:

- `Terkait` — по релевантности
- `Paling Populer` — по популярности
- `Terbaru` — **сначала новые** ← напрямую закрывает требование «сортировка: сначала новые»
- `Harga Terendah` — цена по возрастанию
- `Harga Tertinggi` — цена по убыванию

Также упоминается фильтр по диапазону цены в Rp. То есть **сортировка «Terbaru» и,
скорее всего, ценовой диапазон реализуемы на стороне сервера** — это критично для
`only_recent`: при сортировке по дате можно читать страницы, пока не упрёмся в
границу окна, и прекращать пагинацию досрочно.

Имена GET-параметров для сортировки/цены **не установлены** — нужен живой запрос.

### 1.5. Сигнатура бэкенда

Формат `/id/search?q=product/search&search=<query>` — это узнаваемый роутинг
OpenCart (`index.php?route=product/search&search=`), обёрнутый в человекочитаемый
URL. Префикс `/id/` — локаль (вероятно, есть и `/en/`).

Если бэкенд действительно OpenCart-подобный, ожидаемо: пагинация через `&page=N`,
лимит через `&limit=N`, сортировка через `&sort=`+`&order=`. **Это гипотеза,
основанная на форме одного URL** — проверяется одним запросом.

## 2. Чего установить НЕ удалось (блокеры этапа 0)

Всё перечисленное требует живых HTTP-запросов и **не должно домысливаться**:

1. **`robots.txt`** — содержимое неизвестно. Это блокирующий пункт: до его чтения
   нельзя утверждать, что парсинг `/listing/`, `/store/`, `/p/` и `/id/search`
   вообще разрешён, и неизвестен `Crawl-delay`. **Первое, что надо прочитать.**
2. **Внутренний JSON API.** Не найден и не опровергнут. Не снята вкладка Network,
   не просмотрены JS-бандлы. Неизвестно, SSR это (Next.js `__NEXT_DATA__` /
   `_next/data/*.json`), классический серверный рендер или SPA с XHR.
3. **Точные GET-параметры**: имя параметра поиска, страницы, лимита, сортировки,
   ценового диапазона, категории.
4. **Формат пагинации**: page/offset/cursor, размер страницы, есть ли `total`.
5. **Заголовки**: нужен ли `X-Requested-With`, CSRF-токен, кука сессии, локаль.
6. **Лимиты/защита**: rate limit, Cloudflare, капча, блокировка по UA.
7. **Наличие полей** — главный риск проекта, см. таблицу ниже.

### 2.1. Матрица доступности полей (то, что предписано проверить пунктом 4)

| Поле | Нужно фильтру | Статус | Где искать |
|---|---|---|---|
| Цена | `price_min`/`price_max` | 🟢 почти наверняка есть | листинг, карточка |
| Название, фото, ссылка | карточка выдачи | 🟢 почти наверняка есть | листинг |
| **Дата публикации** | `only_recent` | 🟡 косвенно — epoch-ms в slug (п. 1.3) | slug → верифицировать по карточке |
| Продавец (имя, slug) | вывод | 🟢 ожидается | карточка → `/store/<slug>` |
| **Дата регистрации продавца** | `max_registration_date` | 🔴 **не подтверждено** | `/store/<slug>` — «Bergabung sejak …» |
| **Кол-во отзывов** | `max_reviews` | 🔴 **не подтверждено** | `/store/<slug>` |
| Рейтинг | вывод | 🟡 вероятно есть | `/store/<slug>` |

🔴 — риск проекта. Два из четырёх заказанных фильтров (`max_registration_date`,
`max_reviews`) опираются на поля, наличие которых **не подтверждено**. Если Toco
не публикует дату регистрации продавца, фильтр №1 нереализуем в заданном виде и
потребует замены (например, на дату самого раннего объявления продавца как
нижнюю оценку). Это надо выяснить **до** написания `parser/filters.py`.

### 2.2. Стратегия дозапроса (проектируется, применяется после верификации)

Данные распределены по трём уровням, и это определяет стоимость запроса:

```
листинг/поиск  →  id, название, цена, фото, url (+ epoch-ms из slug)
   ↓ дозапрос карточки — только если даты нет в slug
/listing/<slug> →  точная дата публикации, ссылка на продавца
   ↓ дозапрос профиля — один раз на продавца, потом из кэша
/store/<slug>   →  дата регистрации, кол-во отзывов, рейтинг
```

Порядок работы, минимизирующий число запросов:

1. Тянуть листинг с серверной сортировкой `Terbaru` и, если поддерживается,
   серверным ценовым диапазоном.
2. Отсечь по цене и по дате из slug **до** любых дозапросов.
3. При сортировке по дате — прекращать пагинацию, как только вышли за окно
   `only_recent` (не читать весь каталог).
4. Карточку дозапрашивать **только** для объявлений без epoch-ms в slug — или,
   если п. 1.3 не подтвердится, для всех выживших после ценового фильтра.
5. Профиль продавца — один раз на уникального продавца, результат в SQLite-кэш
   с TTL из конфига. На странице выдачи в 5 объявлений продавцов обычно меньше 5.
6. Фильтры по продавцу (`max_registration_date`, `max_reviews`) применять
   последними — они самые дорогие по числу запросов.

### 2.3. Относительные даты

Если дата публикации отдаётся строкой вида «2 hari lalu», нужен парсер
индонезийских относительных дат → `datetime` (tz-aware UTC). Ожидаемый словарь:
`detik` (сек), `menit` (мин), `jam` (час), `hari` (день), `minggu` (неделя),
`bulan` (месяц), `tahun` (год); `kemarin` — вчера; `baru saja` — только что.
Форма выражения на сайте **не подтверждена** — возможен и абсолютный формат
(`12 Juli 2026`), тогда нужен словарь индонезийских месяцев. Реализовывать надо
оба пути, выбор — по факту.

## 3. Как добить этап 0

В репозитории лежит `tools/recon.py` — он снимает ровно те факты, которых не
хватает, и печатает готовый отчёт. Запускать в среде **с доступом к сети**.

```bash
pip install httpx selectolax
python tools/recon.py --query "iphone"

# с перехватом XHR (покажет внутренний API, если он есть):
pip install playwright && playwright install chromium
python tools/recon.py --query "iphone" --browser
```

Скрипт:

1. читает и печатает `robots.txt` целиком (+ `Crawl-delay`, `Sitemap`);
2. дёргает поиск, категорию, карточку и витрину продавца, сохраняет HTML в `recon_dump/`;
3. ищет в HTML признаки SSR-API: `__NEXT_DATA__`, `_next/data`, `window.__*`,
   inline-JSON, `application/ld+json`;
4. выгребает из HTML и JS-бандлов строки, похожие на API-эндпоинты
   (`/api/...`, `api.toco.id`, `graphql`);
5. в режиме `--browser` пишет **все** XHR/fetch веб-версии: URL, метод,
   заголовки запроса, тип ответа — это и есть искомый внутренний API;
6. проверяет гипотезу 1.3: сверяет epoch-ms из slug с датой, найденной в карточке;
7. пробует OpenCart-подобные параметры (`page`, `limit`, `sort`, `order`) и
   сообщает, меняется ли выдача.

Между запросами — пауза 1.5 с, User-Agent обычного браузера, только публичные
страницы, без авторизации и обхода защиты.

Вывод скрипта переносится в разделы 1 и 2 этого файла, 🔴/🟡 заменяются на факты,
и только после этого начинается написание `parser/`.

## 4. Правовые и этические рамки

- Только публично доступные страницы; никакой авторизации под чужими аккаунтами,
  обхода капчи и приватных данных.
- `robots.txt` соблюдается — читается до первого запроса к контенту.
- Rate limit по умолчанию не чаще 1 req / 1–2 с, настраивается в `.env`.
- Ретраи с экспоненциальным backoff только на 429/5xx; 403 не ретраится.
- `seller.toco.id` и `partners.toco.id` не трогаем.
